# EpiLocate 项目文档维护指南

## 1. 三份项目文档分别负责什么

### `ITERATION_HISTORY.md`

记录项目阶段演进、架构变化、重要决策、集成边界和长期技术债。它回答“项目为什么从一个形态变成另一个形态”。

### `ENGINEERING_JOURNAL.md`

记录真实工程活动。它回答“某个日期、某个任务实际改了什么、遇到了什么、怎样验证”。同一天的 Backend、Frontend、Worker、QA、集成和文档任务分开记录。

### `DOCUMENTATION_GUIDE.md`

说明两份文档的职责、更新时机、证据等级、检查脚本和敏感信息边界。

三份文档都以事实和证据为中心，不替代 API contract、Worker protocol、科研 protocol 或部署手册。

## 2. 当前历史基线

本轮历史基线是：

```text
p0/integration
b069a8ce4fdeb33c7b33e2f5c3b109eb5724b6b5
```

Phase 4.5 之前的历史根据已审计 Git、仓库文档、测试报告和验收材料整理。Phase 5 及以后必须依据当时真实的分支、Worktree、Commit、测试和实现追加，不能预先补写。

并行科研分支不自动等于集成基线。记录科研结果时必须写明分支和它与 `p0/integration` 的祖先关系。

## 3. 证据等级

优先级如下：

1. Git Commit、分支关系和实际文件。
2. 仓库内原始测试报告、QA 报告和机器可读验收材料。
3. 技术合同、架构冻结文件和部署说明。
4. README 或交接说明中的结果摘要。
5. 不能由以上材料确认的口述或推测。

低等级证据可以作为线索，但不能扩展成未记录的开发日期、执行者、问题原因、性能或验收结论。

## 4. 什么时候必须更新

### 必须更新两份工程文档

以下变更完成后，必须同时更新 `ITERATION_HISTORY.md` 和 `ENGINEERING_JOURNAL.md`：

- Backend、Frontend、Worker、AI Node 或系统集成。
- API、数据库、对象存储、部署配置或运行时变更。
- Bug 修复、测试修复、回归和验收。
- 新阶段完成或进入新的集成基线。

工程代码已经完成但文档没有更新，不视为完整交付。

### 可以只更新项目文档

以下情况可以只修改项目文档：

- 纯历史补录。
- 更正已有历史，并附上来源。
- 文档索引、措辞或排版调整。
- 不改变工程行为的文档整理。

历史补录不是代码变更的通用豁免。只要同一变更包含代码、测试、配置或部署文件，就必须同时补充两份工程文档。

## 5. 开始工作时

1. 阅读本指南、迭代史和工程日志。
2. 检查目录级 `AGENTS.md`；如果后续目录增加更具体规则，以更具体规则为准。
3. 确认当前项目根、分支、Worktree、HEAD 和工作区状态。
4. 确认自己的变更不会修改 FrozenBaseline、Checkpoint、研究冻结产物或其他 Codex 的 Worktree。
5. 记录开发前 HEAD，完成后再记录最终 Commit。

## 6. 完成工作时

工程日志至少应包含：

- 日期和任务类型。
- 负责人；无法确认时写“未记录”。
- 分支、Worktree 和开发前 HEAD。
- 完整 Commit SHA。
- 实际修改内容。
- 问题和已确认原因；原因未查明时明确写出。
- 测试、构建、HTTP、浏览器或 E2E 证据。
- 未完成事项和下一步。

迭代史在以下情况下追加阶段记录：

- 一个可独立验收的阶段完成。
- 架构边界或主要技术方案发生变化。
- 进入新的集成基线。

## 7. 状态和边界写法

必须区分：

- 已实现：代码存在。
- 已通过测试：指定测试范围通过。
- 已完成集成：进入指定集成 Commit。
- 已部署：有部署环境和运行证据。
- 尚未完成：未实现、未运行或仍需验收。

以下边界不能省略：

- `MOCK` 不等于 `LIVE_CASE`。
- `LIVE_CASE` CPU 推理不等于 GPU 验收。
- 本地 PostgreSQL/MinIO 不等于生产部署。
- 2D 像素 overlay 不等于 3D registration。
- 模型遮挡响应不等于病灶标注或临床定位准确性。
- 测试通过不等于临床有效性通过。

## 8. 证据引用格式

优先写完整 SHA，而不是短 SHA。文件引用使用仓库相对路径；报告若来自另一个分支，必须注明：

```text
分支：<branch>
Commit：<full SHA>
文件：<path>
与当前基线关系：祖先 / 并行分支 / 未合并 / 无法确认
```

测试数量必须连同测试范围和环境一起写。不要把一个分支的测试结果复制成整个集成基线的结果。

## 9. 多 Codex 并行记录

同一天的任务使用独立小节。不得根据 Commit message 猜测：

- 具体 Codex 执行者。
- 完整实际开发日期。
- 未记录的排查过程。
- 未记录的性能或部署结果。

如果多个任务使用同一日期，分别写清 Backend、Frontend、Worker、QA、集成或文档角色。

## 10. 文档同步检查

检查脚本支持指定基线或范围：

```bash
python3 scripts/check_project_documentation.py --base p0/integration
python3 scripts/check_project_documentation.py --range <base>..<head>
python3 scripts/check_project_documentation.py --base p0/integration --working-tree
```

脚本只检查变更范围和两份文档是否同步，不生成开发背景、问题原因或测试结论。它会：

- 对纯文档变更返回通过。
- 对历史补录输出来源提示。
- 对代码、测试、配置或部署变更要求两份工程文档都出现在同一范围内。
- 在缺少文档时返回非零状态并列出变更文件。

当前仓库没有既有 CI，因此本阶段只建立脚本和工作约定，不新增 CI 工作流。

脚本的正向、反向和纯文档场景测试位于 `tests/test_project_documentation.py`。

## 11. 敏感信息和研究数据

工程文档不得写入：

- 密码、Token、API Key、私钥或签名 URL。
- 真实患者姓名、患者 ID、DICOM 路径或未去标识影像。
- 原始 DICOM、模型权重和私有对象内容。
- 个人机器的绝对私密路径，除非该路径本身是必要的 Worktree 证据。

可以记录脱敏的 Commit、哈希、状态码、测试数量和临时环境类型。

## 12. 历史更正

发现错误时追加更正记录，不静默改写：

```markdown
### 更正｜YYYY-MM-DD｜原记录标题

**原结论：**
**更正结论：**
**依据：** Commit、报告或文件路径
**影响：** 哪些阶段或边界需要重新理解
```

## 13. 交付前检查

- [ ] 当前分支和 Worktree 正确。
- [ ] 代码/测试/配置/部署变更已同步两份工程文档。
- [ ] 阶段记录给出完整 Commit SHA。
- [ ] 分支级结果没有被写成集成基线能力。
- [ ] GPU、生产和临床边界清楚。
- [ ] 没有敏感信息。
- [ ] `python3 scripts/check_project_documentation.py ...` 通过。
- [ ] `git diff --check` 通过。
- [ ] 汇报中列出未完成事项和历史资料不足。
